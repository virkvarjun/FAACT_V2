Chapter 7

Every design choice, and why

A research codebase is a pile of decisions. Most are invisible in the results and decide whether the results mean anything. This is the complete list, grouped by area, with what each one prevents.

Where a choice was changed during the project, both the original and the replacement are shown — the change is usually the interesting part.

7.1  Setup and infrastructure

ChoiceWhyWhat it prevents
Use the published checkpoint, verify it per-seed
rather than retraining		The reference repo ships per-episode results for 500 evaluation episodes. Comparing episode by episode is a far stronger check than comparing averages.Six hours of training on the critical path, and the possibility of a subtly wrong policy that scores plausibly
lerobot as a pinned pip dependency
not a git submodule		v1 pinned a submodule commit that did not exist upstream, so a fresh clone could not be set up at all.An unrunnable repository
Extract features by forward hooks
not by forking the policy		Reads internal activations without modifying or vendoring lerobot.A fork that drifts from upstream and cannot be updated
400-step episodes everywhereFixed once in one module, used by baseline, calibration, labelling and ablation alike.Numbers from different runs that are quietly not comparable
Platform-aware MUJOCO_GL
glfw on macOS, egl elsewhere		EGL does not exist on macOS; the original blanket default failed there.Rendering failing deep inside a long run
Every script is a gate
prints PASS/FAIL, exits non-zero		Makes failure the loud default rather than something to notice later.Pipelines that complete while having done nothing
artifacts/ is gitignoredOutputs are regenerable; the scripts and the README are the source of truth.A repo where results and code disagree about which is current
Long jobs under nohupLearned the hard way: a 90-minute run was killed mid-flight by a wrapper timeout.Losing hours of compute to a dropped session

7.2  Running it on a laptop without cooking it

ChoiceWhy
One torch thread per workerThe single most important knob. Without it each of N workers spawns a thread pool sized to the whole machine, so they contend — slower than running serially, and hotter.
Performance cores minus oneThis M5 has 4 performance and 6 efficiency cores. The E-cores are much slower at MuJoCo, so scheduling onto them adds heat for little throughput and makes the machine unusable meanwhile.
Thermal governor on NSProcessInfo.thermalStateApple's own thermal-pressure API. No sudo, no SMC sampling, no third-party tools. Pauses at "serious", resumes when it drops.
Not pmset -g thermIt reports nothing until a thermal event has already been recorded, so it cannot be polled proactively.
Pause at "serious", not "fair""Fair" is normal for sustained compute — pausing there would stall the job permanently rather than protect anything.
spawn, not forkMuJoCo and torch are not fork-safe.
Per-episode shards written immediatelyA kill costs at most one episode. This was not hypothetical — a run was killed at 33/80 and resumed with zero recomputation.
Projected total printed after episode 1An overrun becomes visible in minutes rather than hours.

Result across roughly 12 hours of labelling: zero thermal pauses, and the machine never left "fair".

7.3  Disturbances

ChoiceWhyWhat it prevents
Four kinds, three hook points
physics / action / observation		Different kinds of failure need different mechanisms. Teleporting the cube is a world edit; forcing a gripper open is an action edit; occlusion is a perception edit.A suite that only tests one failure mode
Hook order: physics → re-observe → observation → act → action → stepThe re-observe is load-bearing. Without it the policy acts on an image of where the cube used to be.A disturbance the policy cannot perceive, which looks far stronger than it is
All randomness drawn in bind()
not lazily at each hook		Makes a disturbance a pure function of its spec, so replaying an episode from a snapshot reproduces it exactly.Branch rollouts that silently experience different disturbances
Every disturbance records whether it firedDirectly targets v1's fatal bug.An unperturbed episode counted as perturbed
Two exception types, not onePerturbationNeverFired means the episode ended before the onset — legitimate, exclude and count it. A plain RuntimeError means it ran past the onset and still did nothing — a real defect.A long sweep crashing on ordinary data, or a real bug being swallowed
Onset window from measured task timing
40–160 → 150–280		First cube contact is at median step 154. The original window fired almost entirely before the grasp.Half the dataset being disturbances that do nothing
Onset randomised within the windowSo the model cannot learn "trouble always starts at step 120".A predictor that has memorised the schedule
Gate = in-band AND ≥15 point dropWith a 65% baseline, a disturbance that does nothing scores 65% and passes an absolute 25–65% band. grasp_slip passed it four times while having no effect.Calibrating a disturbance that does not disturb
Duration is overridable per kindFor grasp_slip, duration is the only meaningful knob — the gripper is either forced open or not.A magnitude sweep that varies a parameter the kind ignores

7.4  Measuring reversibility

ChoiceWhyWhat it prevents
mjSTATE_INTEGRATION (262 numbers)
not get_state() (45)		The 45 omit the constraint solver's warm-start cache, so branches diverge from identical snapshots.Every label inheriting compounding numerical error
Snapshot carries the step counter tooIt lives in a gym wrapper, outside MuJoCo entirely.R collapsing to (branch 0 won)/8 with no error raised
restore() rejects a raw array
requires a SimState		Passing bare physics is exactly the mistake that caused the counter leak. The type system now refuses it.The same bug returning later
Branches run open-loop at h=100A 250-step branch costs ~3 policy forward passes instead of 250. The label is about whether recovery is possible, not how cleverly you drive afterwards.A 10× larger compute bill for no extra information
M = 8 branches, stride 25Budget compromise. 16 label points per episode at 8 branches is ~2.6M simulator steps for 80 episodes.—
Per-branch Gaussian action noise, σ=0.01Restore is bitwise exact and ACT is deterministic, so without noise all 8 branches are identical and R can only be 0 or 1. σ chosen by sweep: 0.01 leaves baseline success unchanged at 65%, 0.02 drops it to 40%.Eight identical branches, or a noise level that biases every label downward
Branch seed = timestep×10000 + indexNo two branches anywhere in the dataset share a noise sequence.Correlated branches inflating apparent agreement
Restore once more after labellingLeaves the episode exactly where it was.Measurement perturbing the thing being measured
Branches do not re-apply the disturbanceA definition, stated explicitly: R is recoverability of the state you are now in, under undisturbed future dynamics. Faithful for physics-level disturbances, noted as slightly optimistic for occlusion.An unstated assumption doing silent work
Shard filename encodes every label-determining settingStride, branches, noise, horizon, max steps, onset window, magnitude. Not just the seed.Silently serving labels measured under a different disturbance — and it converted a real incident from corruption into a recoverable mistake
Loader refuses mixed configurationsTwo labelling configs in one directory would be concatenated without complaint. Different kinds still mix freely, since that is intentional.Training on a mixture nobody chose

7.5  The model

ChoiceWhyWhat it prevents
Same MLP shape as v1's predictor
input → 256 → 128 → 1		Deliberate. If v2 works and v1 did not, the difference is then the target quantity, not the architecture.Confounding a better target with a better network
Sigmoid + soft-target BCE
not MSE		Labels are fractions (wins/8). BCE against a soft target is the proper scoring rule and is better calibrated near 0 and 1 — exactly where the controller acts.Systematic miscalibration at the extremes
Splits by episode, never within oneStates 25 steps apart share a seed, a disturbance, and often a chunk. They are near-duplicates.A model that looks calibrated and is worthless
5-fold CV with pooled out-of-fold predictions
not a single split		A single 24/8/8 split chose a feature set at ρ=0.509 on validation which then scored 0.265 on test — a 0.24 swing on the same model.Drawing conclusions from an 8-episode test set
Feature groups swept, selected on validation1206 dimensions against ~300 training states overfits. Which subset generalises is empirical — but choosing it on test would make the reported number meaningless.Selection bias masquerading as a result
Standardiser fit on training states onlySame leakage rule as the split.Test statistics leaking into training
Hooks assert they firedA silent hook yields zeros; a model trained on zeros predicts the mean and looks like "these features aren't informative" rather than like a bug.A bug diagnosed as a negative result
Features concatenated in sorted key orderA vector built today lines up with a model trained yesterday.Silent feature misalignment
Per-fold heads saved alongside their held-out episodesLets the ablation score each episode with a model that never trained on it, making the learned controller directly comparable to the oracle.Flattering the learned side exactly where it is being compared
Report Spearman, not just lossThe controller only needs the ordering of states to be right; it maps R to a horizon monotonically.Optimising a metric the application does not use
Report a predict-the-mean baseline alongsideA model can post a respectable correlation while being no better than the mean in absolute error.A correlation that impresses and means nothing

7.6  The controller

ChoiceWhy
h = clip(h_min, 100, 100·R̂γ)Monotone in R, bounded, and with one interpretable knob. γ>1 makes the controller shorten sooner as R falls.
h_min raised 5 → 20h=5 measured 0/40 because the arm stalls there. A controller whose floor sits in the collapse regime is punished for reacting, which inverts the entire intent of gating.
Gated and risk-gated share one code bodyThey differ only in which scalar they consume — which is precisely the comparison being made.
Oracle interpolates between labelled timestepsLabels exist every 25 steps. Defaulting unlabelled steps to a constant would quietly degrade the oracle into a fixed-horizon policy.
Temporal ensembling offIt blurs what "committed for h steps" means, and the commitment horizon is the entire subject.
Executor is pull-based
action = ex.act(t, obs)		The caller keeps the environment loop, so every condition in the ablation is one horizon_fn against one identical loop.
Horizon outside [1, chunk_size] raisesZero would replan forever without stepping; longer than the chunk would index past its end. Both are controller bugs.

7.7  Evaluation and statistics

ChoiceWhyWhat it prevents
Identical seeds and disturbances across conditionsOnly the horizon rule changes.A success-rate gap that cannot be attributed
Conditions aligned to their common episode setShortening the horizon changes when episodes terminate, so exclusions genuinely differ between conditions.Comparing six slightly different experiments
McNemar, not a two-proportion testThe conditions are paired; treating them as independent throws that away and loses power.Underpowered analysis of an already-underpowered design
Bonferroni stated, not quietly ignored15 pairwise comparisons at α=0.05 expect 0.75 false positives even under a true null.Reporting p=0.013 as a finding
Power analysis reported"Not significant" at n=76 means "underpowered", not "no effect" — and equally is not evidence for the method.Both possible misreadings
Lead time relative to each episode's own first horizon
not an absolute threshold		Under an absolute 50-step cutoff, fixed h=20 scored as "reacting" at every step of every episode — lead time −106 on 30/30, false alarm 100% — purely because 20 < 50.Fabricated reaction statistics for constant-horizon policies
False-alarm rate reported beside lead timeWithout it, a controller that always shortens scores perfectly on lead time and is useless.A metric that rewards panicking
Mean horizon pooled over replans, not episodesOne long commitment should not outweigh four short ones just by being its own episode.A misleading average

7.8  The demo videos

ChoiceWhy
Pairs selected by outcome divergenceA pair where both policies succeed demonstrates nothing. If no pair diverges the script writes no file and says why, rather than producing a persuasive-looking video that shows no difference.
Captions show the live task stage
not the final verdict		The first version burned the episode's outcome onto every frame, so a run read "SUCCESS" from step 0 before the robot had done anything.
Held frames dimmed and captionedWhen one episode ends early its last frame was silently duplicated, which reads as the simulation hanging.
Frames held rather than truncatedTruncating to the shorter episode would hide the outcome of the longer one — usually the failure.
A two-fixed-horizon mode was addedThe script originally only compared fixed against gated, which structurally cannot show the cliff — the project's clearest result.
