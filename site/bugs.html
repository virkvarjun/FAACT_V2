Chapter 6

Six bugs that produced believable numbers

None of these crashed. Every one produced plausible output while being wrong. This is the most transferable material in the whole project, because the pattern generalises far beyond robotics.

The pattern

In a pipeline that trains a model, runs a simulator, and reports a statistic, failures do not announce themselves. A crash is a gift — you know immediately. The dangerous failures are the ones where every stage completes, writes its output, and reports a number that sits in a believable range.

Five of the six below were caught by checks written to make the pipeline refuse to proceed — assertions, gates, guards. Exactly one was caught by a human looking at the output and asking why it seemed odd.

Zero of them were caught by noticing a wrong result. The results all looked fine.

1 · The disturbance flag that did nothing

WhereFAACT v1
Symptom0/20 baseline, 0 recoveries, in every run
Cause--perturbation_mode was parsed and stored, never used
Caught bypost-mortem, after the project had concluded

The entire premise of v1 was recovering from disturbances. No disturbance was ever applied. The pipeline ran end to end, rendered videos, computed metrics and produced a results table — all describing an experiment that had not been performed.

The fix, in v2: every disturbance object records whether it fired, and the episode runner raises if an episode completes without it firing. Two distinct exception types separate "the episode ended before the disturbance was due" (legitimate, exclude and count it) from "the episode ran past the onset and it still never fired" (a bug).

2 · The solver cache that wasn't in the snapshot

Wherev2 branch rollouts
Symptomtwo branches from an identical snapshot diverged by 2×10−8
Causephysics.get_state() omits MuJoCo's constraint-solver warm-start cache
Caught bya test asserting bitwise reproducibility

MuJoCo's solver is iterative and warm-starts from the previous step's solution. That cache is not among the 45 numbers dm_control returns. Restoring without it means the solver begins from a different guess and produces a marginally different answer, which compounds.

physics.get_state()      45 numbers   → divergence within 150 steps
mjSTATE_INTEGRATION     262 numbers   → bitwise identical

Why the test had to demand bitwise equality. A tolerance-based check ("agree to 6 decimal places") would have passed. The divergence is tiny at first and grows, so only an exact-equality assertion catches it at the point where it is still cheap to fix.

3 · The step counter that survived a restore

Wherev2 branch rollouts
Symptomnone — the numbers looked entirely reasonable
Causethe episode step counter lives in a gym wrapper, not in MuJoCo
Caught bya test asserting all branches get equal step budgets

Restoring physics does not touch the TimeLimit wrapper's counter. From a snapshot at step 120:

branch 0:  ran 280 steps
branch 1:  ran   1 step      ← counter already at the 400-step limit
branch 2:  ran   1 step

Every branch after the first was truncated immediately. R would have silently become (did branch 0 win?) / 8 — taking only the values 0 or 0.125, looking exactly like a probability, and meaning nothing. Every downstream result would have inherited it.

The lesson that generalises: when you snapshot "the state", enumerate where state actually lives. Here it was split across a physics engine and a Python wrapper, and only one of them was obvious.

4 · Disturbances aimed at the wrong phase of the task

Wherev2 disturbance design
Symptomgrasp_slip scored 65% at every duration — identical to undisturbed
Causethe onset window was steps 40–160; the cube is first grasped at step 154
Caught bya calibration sweep that measured each disturbance's actual effect

Forcing a gripper open when it is not holding anything does nothing at all. Roughly half the labelled dataset consisted of episodes whose disturbance had no effect — effectively unperturbed episodes sitting in a dataset about recovering from disturbances.

Fixing it required first measuring the task's own timing (first contact at step 154, transfer complete at 278) and moving the window to 150–280.

And a flaw in the check that was supposed to catch it

The acceptance test asked only whether perturbed success landed in a 25–65% band. With an undisturbed baseline of 65%, a disturbance that did nothing scored 65% and passed — which grasp_slip did four times in a row, printing "IN BAND" each time.

The gate now requires a drop of at least 15 points against the undisturbed rate on the same seeds, not merely an absolute range. An absolute band cannot distinguish "correctly calibrated" from "does nothing" when the baseline sits at its edge.

5 · The directory flag that worker processes never saw

Wherev2 parallel labelling
Symptoma directory reported 83 episodes when it should have held 80
Cause--shard-dir set a module-level global; spawn workers re-import the module and never see it
Caught bynoticing an unexpected episode count while comparing two datasets

A three-hour labelling run was writing its output into the previous dataset's folder. Multiprocessing with the spawn start method re-imports the module in each worker, so anything assigned to a global in main() is invisible to them.

What limited the damage: an earlier fix had already put every label-determining setting into the shard filename — stride, branch count, noise, onset window, magnitude. So the two datasets did not collide by name and nothing was overwritten. They were separable and were separated. Had the filename still been keyed on the episode seed alone, the new labels would have silently overwritten the old ones.

The loader now refuses to open a directory containing more than one labelling configuration, while still permitting the legitimate mixing of different disturbance kinds.

6 · The mechanism that was assumed, not measured

Wherethe written explanation of the central result
Symptomnone in the numbers — the numbers were right
Causea plausible mechanism was asserted without checking it
Caught bya human watching the videos and asking why the arm wasn't moving

The claim was that short horizons make ACT "tear itself apart": because actions are absolute joint targets, each replan jumps to a different target and the motion becomes jerky and self-destructive. It is a reasonable story. It is also wrong.

MEASURED — net joint displacement over an episode:
  h=5     0.16      the arm barely leaves its start pose
  h=100   2.02

The arm does not thrash. It stalls. An ACT chunk begins at the current pose, so committing only its first few actions and replanning from a barely-changed state re-emits a near-identical chunk. The robot creeps forward at a fraction of speed and runs out of time.

Why no automated check caught this. Every number was correct — h=5 really does score 0/40, replicated on two independent seed sets. Only the explanation was wrong, and no test asserts that a written explanation matches reality. The rollout videos existed, but had been generated late and not watched carefully.

What to take from all six

  • A flag that does nothing looks exactly like a flag that works. Anything that is supposed to have an effect should be asserted to have had one.
  • Enumerate where state actually lives before writing a snapshot function. Physics engine, wrappers, RNGs, counters — all of it.
  • Demand exact equality where exactness is achievable. A tolerance would have hidden bug 2 until it was expensive.
  • An acceptance band on the wrong quantity passes trivially. Bug 4's check compared an absolute rate when it needed to compare a difference.
  • Put every setting that changes an output into that output's filename. It converted bug 5 from silent corruption into a recoverable mistake.
  • Watch the raw output. The one bug no check caught was caught by looking at a video. Aggregate statistics cannot tell you the arm never moved.

Four separate conclusions in this project also reversed under better tests: that a more accurate estimator would help, that calibration would help, that the oracle beat the baseline, and that success was monotone in horizon. Being wrong repeatedly and finding out is the process working, provided the finding-out is built in.
